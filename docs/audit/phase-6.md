## Goal and scope

The owner-defined scope in `plan.md` is the baseline: boot/off/no-signal/BIOS/OS/restart/install/failure phases; pending and applied BIOS settings and boot drive; software/files/folders/storage, program install/uninstall, USB/OS clone; monitor/case/component LCD binding, aspect/curved-display handling and shared desktop/app/taskbar/window state with simultaneous input from both players. Input identity must remain per player while mutations of shared PC state are consistently ordered. There is no exclusive desktop-control lock. Tablets are personal models; observers need remotely visible screen/activity. Stock wallpaper content is in scope; automatic custom asset transfer is planned under phase 12.

The end state is not achieved by synchronizing rendered pixels alone. The recommendation is a layered model: synchronize the PC's durable OS/software/configuration state and the shared desktop's logical window state; route player-authored semantic actions to the host for ordering; locally replay/render the accepted state on all displays. Streamed or captured pixels may be a later fallback for surfaces whose apps cannot be made deterministic, but must not be the source of truth for save/late join.

## Proposed architecture for implementation planning

1. **Separate durable PC image from presentation.** Define a serializable `PcOsState` keyed by `NetObjectId` (or a stable in-PC identity) for verified persistent OS facts: BIOS config/boot selection; installed OS/programs; files/folders/storage; clone/install outcomes; approved stock wallpaper identifier; any game-provided OS data that inspection proves is PC-owned. Preserve unknown native fields instead of rebuilding from a partial model.
2. **Represent shared desktop as a logical scene.** Keep per-PC running app IDs, open window IDs, normalized bounds, z-order, focus/minimize/maximize, start-menu visibility, desktop size/aspect, and app-specific state only where that app can be safely modeled. Each game renders this state into its own active `VirtualComputer`/monitor scene. Stable IDs must not be Unity instance IDs.
3. **Submit semantic player intents, apply confirmed result.** Input envelopes carry actor ID/epoch, operation ID, PC ID, UI target/window generation, action and normalized pointer location as needed. The host validates current ownership, PC stage, target generation and app preconditions, then orders the mutation. Both peers apply the accepted mutation to the logical model and update local Unity UI. This allows concurrent players without a desktop lock; host ordering resolves simultaneous edits.
4. **Keep local selection/pointer identity separate.** Hover, cursor position, pressed buttons and drag capture belong to each actor. The shared screen renders two labeled pointers, one per player, as decided by the owner; both pointers can click. Pointer input must be distinguishable from resulting shared state; cursor/hover positions may be ephemeral and need not be saved, while active drag state must be canceled safely after packet loss.
5. **Use game-native flows only for bounded side effects.** For install/uninstall/clone/restart, inspect callbacks and create an explicit operation lifecycle (begin/progress/commit/cancel) analogous to component edits. The accepted durable result should be applied once; never rerun install/boot achievements, job progression, random generation or global notifications on both peers without isolation. If exact deterministic replay cannot be demonstrated, the operation should be host-executed and its canonical result replicated.
6. **Treat display bindings as projections.** Map a shared PC logical screen onto each local physical monitor/case LCD; support curved monitor camera/raycaster and aspect changes as local render projections. The remote view/activity should describe which PC/display is active and show a safe representation even where no local monitor is present. Do not couple one player's tablet focus/UI singleton to the other's.

### Mouse-pointer owner decision

**Owner decision recorded during this audit:** show two labeled mouse pointers on the shared desktop; both players can click. This is a requirement, not an open option. It fits actor-scoped input and simultaneous interaction. Implementation must determine if `PointerInputModule` can host separate pointer IDs across all monitor UI, including pressed/released/drag state; otherwise add an adapter that retains actor ID and translates monitor-space coordinates. Resolve pointer overlap and simultaneous hits by host order. A pointer may move without changing durable OS state, so its replication frequency/lifetime and whether pointers disappear outside monitor interaction remain implementation details to settle by a focused probe.

## State, input, pixels

- **Durable state replication is required** for saves, Continue, guest snapshots and late join. Synchronize canonical OS/software/configuration results and the shared desktop scene model, with versioned validation and deterministic IDs.
- **Input replication is needed** for live collaboration. Replicate semantic intent and actor identity, not raw operating-system mouse deltas or arbitrary Unity events. Host ordering plus explicit per-actor drag/input state handles races; accepted outcomes update all viewers.
- **Pixel replication is not a sufficient core path.** It makes screens look identical but doesn't update native game state, PC saves, app simulation, or late join; it also complicates per-player input and monitor geometries. Consider it only as a bounded compatibility path for nondeterministic visuals or specific apps, with state still canonical elsewhere.
- **Hybrid recommendation:** durable models + semantic event stream + local native rendering, with per-app snapshot fallback only if implementation probes show a view cannot be reproduced deterministically. This is an architecture recommendation, not permission to broaden app scope beyond phase 6.

## Persistence, late join and versioning

- Snapshot/late join needs both existing native PC records and the additional OS state registered as `IWorldState`; host generation should publish it only once the world and PC mappings are ready. Held world changes must be replayed after guest load.
- Host autosave, Exit, Save screen and `/sync` must capture a settled OS state atomically with the native save and `.coop` sidecar. Existing rules skip game autosaves in co-op; new OS capture must follow the same host save boundary and never persist an unconfirmed local-only click.
- On Continue, do not replay the boot/install lifecycle as if fresh if the durable model says the OS is installed/running. Rebind OS state after native PC load; decide whether active windows restore or boot to desktop based on the game’s normal single-player behavior and owner policy.
- Any change to `.coop` serialized state or native fields written into the sidecar requires a mod version bump. Add prior versions to `CoopSavePair.SameFormat` only after proving identical save schema; otherwise phase 8 migration/refusal applies. Network message changes also require a bump under repo versioning policy.
- Personal tablet state needs an explicit rule for disconnect/late join and should not be serialized into shared PC state unless product scope changes.

### 6c static input seam after the GPU incidents

Read-only native inspection found that `LookingAtMonitorState.Tick` polls `InputModule.GetLocalCursorPos`, checks screen bounds, then uses a world ray or `UnityExt.Raycast` against the OS `GraphicRaycaster`. The game's `InputModule` has one global local cursor and fixed mouse button IDs. Its inherited pointer dictionary being keyed by integer ID does not make the game's concrete mouse processor multi-pointer. Copying a remote position into `SetLocalCursorPos` would overwrite the local player's input. The relevant metadata entries are `LookingAtMonitorState.Tick`/`UpdateInteractions`, `InputModule.Process`/`ProcessMousePress`, and `WindowFrame.OnMouseDrag`/`OnControllerDrag`; the native bodies show local cursor reads inside drag handling. No runtime alias or concrete active raycaster is claimed from metadata addresses alone.

The implementation seam is actor-scoped normalized monitor coordinates and button transitions, keyed by the shared PC, with host ordering and separate per-actor drag capture. A host-resolved pointer event can use the active OS raycaster and an actor-specific `PointerEventData` ID. Persistent app results must be projected from the host; dispatching the same app click independently on both games can duplicate side effects. Text focus must remain actor-scoped rather than writing both players into `EventSystem.currentSelectedGameObject`. The opt-in probe now logs the active event module, PC binding and flat/curved raycaster objects on monitor entry, without screenshots. A safe runtime run is still needed to learn the exact coordinate mapping and whether the UI remains raycastable while the host looks elsewhere.

Offline implementation has begun: player-state packets carry one transient normalized monitor cursor, the plugin has local/remote labeled desktop overlays, and a model-only command handler validates independent actor Down/Drag/Up/Cancel captures with host ordering. These paths compile and the network suite passes 568 checks. The command handler is not registered or connected to native pointer dispatch; remote clicks, typing, shared windows and software results are **not synchronized** by these changes. The cursor coordinates and overlay have not been tested in game.

### 6b software record follow-up (static only)

`ComputerSave.m_software` is an accessor for the boot drive's `PartInstance.m_software`, not an independent field on the PC. Its fields include wallpaper IDs, installed program IDs, LED settings and presets, scan/aspect flags, folder data, AutoExec, a benchmark record and a unique ID (`ComputerSoftware` metadata). `FolderData` has file/folder identity and content fields. The game's software constructor seeds random folders when data is missing, so copying a peer's record by constructing a fresh object would diverge. A USB clone drive has its own software payload through `USBDrivePartInstance.GetClonedSoftware`/`SetClonedSoftware`; its save behavior still needs verification. OS install/copy paths are `ComputerSave.InstallOS`/`InstallCopyOS`, and `AddProgramInstall` mutates the PC's software during its install sequence. These are source observations, not verified native projection seams.

The implementation boundary is the accepted change to a PC's durable software record, after any install/uninstall/copy coroutine settles. A host command should carry a validated software delta or snapshot and apply it without repeating OS install, app or achievement side effects. Native save/snapshot already carries the host's PC record, but live guest projection and clone-drive contents need explicit checks. The visible desktop/window model remains separate, transient state; Save/Continue follows the game's normal boot behavior per owner decision.

## Mirrored desktop input (0.19, November 1, 2026)

### Owner decisions (November 1, 2026)

- **Mirror input**: every click, drag, scroll and key on a shared PC's desktop also runs on the other game, so both games run the same real apps (not a video stream, not window-list-only sync).
- **Instant locally**: a player's own input acts at once on their own game and is sent to the other game at once. Simultaneous conflicting clicks can split the desktops; the open-apps reconcile and `/sync` repair that.
- **Live BIOS**: BIOS navigation mirrors too; Apply / Factory Reset stay the 0.18 host-ordered BIOS command, so the saved setting changes once.
- **Benchmark results**: the host's result is the one kept (its software record wins). 3DMark scores are computed from the hardware (no random input in `ThreedMarkApp`), so both games normally show the same score; only `ComputerSim` temperature readings add random noise.
- **Tablets** stay fully personal (not captured, not replayed).
- Earlier: two labeled pointers, both click; Save/Continue follow the game's normal boot.

### Design

- **Command 11 `DesktopInput`** (`DesktopInputWorld`, replaces the unused 0.19 `MonitorInputWorld`): a batch of up to 64 events of one actor on one PC: `Move`, `Down`, `Up`, `Scroll`, `Text` (field path + full text), `Submit`, `Leave`, `EnterBios`, `Windows` (host only: open app IDs). Coordinates are fractions of the PC screen's root canvas, so different window resolutions and monitor shapes map to the same point. The host only checks the actor epoch and that the PC is benched (releases pass after a move); there is no desktop lock. Nothing is saved.
- **Capture** (`NativeDesktopInput`): while this player is in `LookingAtMonitorState` on a bound bench PC, the screen is Desktop (`InOS` + desktop canvas), BIOS (`IsInBios`, checked first: `IsPoweredOn()` reads false in BIOS) or Boot (`m_on`). The pointer is the local cursor mapped through the root canvas's event camera (curved monitors: the mesh's texture coordinate). Mouse buttons come from `Input.GetMouseButton` (Rewired fallback), the wheel from `Input.mouseScrollDelta`. A click that opens the monitor is not sent (buttons held on entry, and presses in the first 0.5 s). The focused TMP or legacy input field's text is sent whenever it changes (path = sibling indices from the root canvas), Enter as `Submit`. Moves are coalesced and sent at most 30 times a second; anything else is sent the same frame.
- **Replay** on the other game: a virtual pointer per actor (`PointerEventData`, pointer ID 7700 + actor) runs Unity's own sequence through `ExecuteEvents` (enter/exit, down, initialize-potential-drag, begin/drag/end drag, up, click, drop, scroll). The OS canvas is world-space and its event camera is the camera of whoever looks at it (run mirror-1: `MonitorCamera` while looking, null otherwise), so the replay places a disabled helper camera square in front of the screen and makes it the canvas's camera only while the replayed event runs. `WindowFrame` drag/resize read the press camera, so windows move by the same amount. Hits inside `VirtualComputer.m_screenBlocker` (shown on a screen nobody is using) are skipped. The selection is given back afterwards, and an input field a replayed click focused is switched off for five frames so this player's keys never type into it; the other player's typing arrives as `Text`. Events wait up to 4 s for this game's PC to reach the same screen (boot timing), then are dropped with a `[desktop]` warning. Replayed native code runs inside `NativeProjection` with `NativeDesktopInput.Injecting` set; the BIOS Apply/Reset intercepts do nothing for a replayed click (the editor's own request brings the result).
- **BIOS entry**: the boot coroutine opens the BIOS when `PCBSInput.m_enterBios`/`m_enterBiosAlt` is held while the current state is `LookingAtMonitorState`. When the other game entered a PC's BIOS, this game's `VirtualComputer._StartupSequence_d__69.MoveNext` runs with the key read as held (`NativeEditReplay.InputGuard`) and a stand-in `LookingAtMonitorState` as `GameController.m_currentState` (restored in the postfix), for up to 20 s; a desktop already past the prompt is restarted into BIOS.
- **Power**: the power key in `LookingAtMonitorState.Tick` and Start menu → Shut Down call `Motherboard.TurnOn/TurnOff` directly; inside those two scopes the call becomes the phase 5 `Power` gesture (`RequestPower`). Restart from the Start menu is mirrored as a click (power stays on).
- **Open apps** (`NativeDesktopInput.Windows.cs`): the host publishes each desktop's open app IDs when they change and when a guest presence arrives. The guest opens/closes apps (`OS.Launch` / `OS.CloseWindow`) to match once its desktop has been quiet for 3 s. A PC still on its boot screen 20 s after the host reported its desktop is restarted once: a PC that was on when the guest loaded the world hits an exception in the game's boot coroutine (`JobTutorialHintUi.SetSpriteAssetForText`, run mirror-8) and stays on the boot screen.
- **Software record**: the host still publishes each OS PC's boot-drive record (command 12) once it is stable. The guest now compares it with its own and adopts the host's only when they still differ after both were stable for 2 s and no mirrored input for that PC is waiting. Installing an OS and a PC's first power-on generate random files on each game (`ComputerSave.InstallOS` → `ComputerSoftware` ctor/`Init`, `VirtualComputer.FindSim` → `InstallRandomUserFiles`), so this is still needed.
- **Pointer labels**: the overlay is a nested canvas (sorting 30000) on the screen's layer, under the root canvas; each player sees their own name at their pointer and "+ Host"/"+ Guest" where the other player's pointer is (transient `PlayerState.Cursor`).
