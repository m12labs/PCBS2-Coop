## Decisions and boundaries

The [owner decisions](../../plan.md#owner-decisions) require shared inventory, two players in the default Free Build workshop, independent cameras/input, pass-through players, and different-part work on the same PC. Conflicting edits and movement/storage/sale of an actively used PC must be blocked. Drop-in join while a player carries a PC remains required; phase 2's empty-hands admission gate is a gap to remove, not a new scope question.

**Owner answer, October 25, 2026:** when a guest disconnects, or a co-op save loads without a carried PC's carrier, move that PC into shared cupboard storage. Preserve its identity and contents and release departed actor reservations. Do not delete it or give it to the host's local carrier. No carrier-departure choice remains pending.

Phase 3 establishes identity and location before live component installation, cable editing, boot/simulation and full avatar animation. Existing PC contents must survive transfers and snapshots. Movement already has native power/cable side effects, so preserving a populated PC cannot be reduced to moving its transform. Existing UI placement/flow is not redesigned by this audit; any newly required flow still goes to the owner before dependent implementation.

## Acceptance cases

1. Fresh default and populated continue worlds agree on physical IDs, baseline topology, location and peripheral bindings. Duplicate same-SKU objects remain distinct; the same Free Build catalog entry can mint two physical PCs.
2. Race pickup, contested drop, retrieval/delete and repeated operations: one accepted owner/location, chosen rejection feedback, no callback-driven duplication. Retired IDs never resolve to future objects.
3. Independent benches/cameras remain independent. Both actors can enter work on one PC; movement/storage/delete is blocked until relevant claims release. Phase 4 later verifies simultaneous different-part commits.
4. Populated/running connected PC: bench → carrier → another bench → storage → carrier → bench. Preserve parts/config/provenance and agree on required power/cable outcomes; never rebind an unrelated workstation.
5. Spawn/switch while the other actor carries a PC; delete allowed empty/stored PCs. Receiving carrier/input/camera remain local, and replacement/deletion happens once.
6. If reachable, package add/open/empty and physical-note transfers retain singular contents/association. Otherwise record evidence and explicit destination rather than claim support.
7. Save, late join, rejoin and host restart with benched/stored/carried PCs: native+mod state describes one revision and restores IDs/allocator/associations once. Pending reconstruction never leaks a partial capture.
8. Disconnect during pickup, carrying, store and retrieval: move departed actor's PC into shared storage once, preserve identity/contents and release claims. Apply the same rule on load without that carrier. Stale callbacks cannot resurrect an old object/session. Host departure still returns the guest to menu; pause does not stop sync.
9. Stale/malformed/retired/wrong-actor/occupied/loading-target requests preserve the world. Projection failure produces repair/re-admission rather than silent divergent success. Compare logical summaries and visible results on both peers with disposable saves and owned instances.

### Implementation contracts

- [`ObjectWorld`](../../src/PCBS2Coop.Network/ObjectWorld.cs) owns a durable world UUID, monotonic allocator, location manifest, PC and part IDs, origin/creator/operation, per-PC native field/slot links, location/carrier and tombstones. Parsing validates the complete candidate before publication. Every issued ID is accounted for as live or retired. Aliased fields inside a PC share a logical part; the same native pointer in another PC gets another identity. Collection counts, text, total IDs and topology are bounded; exhaustion fails explicitly.
- [`ICanonicalCommandHandler`](../../src/PCBS2Coop.Network/WorldSync.cs) optionally builds host-accepted bytes after validation. Validation/canonicalization propose IDs without committing facts; `Apply` commits them on both peers. Stream hashes cover the accepted bytes. Deduplication runs before canonicalization. Requests cannot append an assigned ID; over-sized canonical results consume no ID/revision. Existing handlers keep the original payload contract.
- [`NativeObjectState`](../../src/PCBS2Coop.Plugin/NativeObjectState.cs) binds a checked workshop manifest built from hierarchy, slot category, stage, delivery and workstation discriminators. Native save/storage positions are binding coordinates within a particular paired save, never durable IDs. All PC records, slot paths, SKUs, native subtypes and alias partitions must match before admission/replay. Part traversal includes direct fields/arrays, proxy/generated-copy/fan relations, motherboard/CPU and water-block references, radiators, cable sets, loops, LED strips and pipe endpoint references. Full native bytes retain condition, software, customisation and provenance fields beyond these identity links.
- Native `GetComputerRef` returns the **address of the bench's save field** (ISIL ends in `LoadAddress rax, [rdi+272]`), despite the generated binding's object return. C1 failed explicitly with an IL2CPP garbage-collected-object error. The adapter uses the evidenced `GetComputer` path. Empty C# declarations alone did not reveal this issue.
- [`ProjectionBindings`](../../src/PCBS2Coop.Network/ObjectWorld.cs) tickets contain world UUID, logical ID and a monotonic attempt number. The native adapter gives each load a distinct spawn callback token and binds only its current completion. Wrapping `LoadComputerToSlotDelegate` directly failed in C4 because `LoadComputerOperation` is non-blittable. The corrected wrapper uses `UnityAction<bool, Case, BenchSlot>` and observes completion from `LoadComputerToSlotAsync`; it preserves the game's original callback. Mapped save wrappers are kept alive (one latest record per PC), and obsolete mesh pointer keys are removed before replacement, so native GC/address reuse cannot turn a stale observation key into another PC's identity. Forced native projection repair remains 3f/3h.
- [`CoopSavePair`](../../src/PCBS2Coop.Network/CoopSavePair.cs) binds the native file's length/SHA-256 to the exact world-state position and up to two full carried-PC graphs. Disk saves use `<native-file>.coop`, published through a flushed temporary file and atomic rename after the native writer settles. A crash between native and sidecar writes is detected as an incomplete/mismatched pair. Admission/copy transfers carry a single bundle over the existing hashed chunk transport. Guest session files and the latest joined copy retain both files. Native-only pre-0.4 co-op saves fail explicitly; solo saves are unaffected. Migration remains phase 8.
- Identity metadata stays under the existing 1 MiB mod-state limit; each carried native graph is bounded at 4 MiB and travels in the chunked bundle, not the snapshot mark or a command. The entire bundle remains under 64 MiB. Oversized/imported graphs fail rather than truncate. C2/C3 byte-for-byte native serializer round-trips measured 1,165,140 bytes for the MSI PC and 1,038,058 for the be quiet PC.
- Only the matching local actor's PC enters the native carry singleton. A present remote host's graph stays in mod memory, outside the guest's hands and interactable storage; its mesh is 3f work. Host resume moves absent carriers into native shared storage before spawning, then changes their logical location while preserving IDs and contents. Both carrier graphs have explicit ID bindings. Encountered carried packages/physical notes fail this capture path with a reason until the 3g adapter exists.
- Capture occurs on the main thread before the native save starts. Saves during native loads or an unfinished paired write are refused with a log/status reason; the previous complete pair is retained. Peer changes held during a snapshot load replay only after full binding validation. The new host generation restores saved mod facts but starts its revision/hash stream afresh.

### Implementation contracts

- [`PcLifecycle`](../../src/PCBS2Coop.Network/PcLifecycle.cs) (command type 3) is a canonical host-ordered handler with four actions. **Create** names a catalog entry (SKU, native type, ordinal among equal entries) and the requester's carried case to replace, if any; the host validates actor epoch, the requester's carrier slot, movement activity and host-native preconditions, then appends the PC and part IDs and the topology both peers must reproduce. **Delete** names a carried (requester's own) or stored PC; every PC/part ID becomes a tombstone once. **Observe** (host only) reports where the host's own native PCs are, so host moves keep both models identical until 3f's atomic transfers replace it. **Extend** (host only) gives parts a native load added to a created PC (default fans) host-ordered IDs; it runs right before every host save/snapshot capture, accepts only pure growth and leaves any other native change to the capture (phase 4).
- A guest's model can lag the host's allocator when a host capture issued IDs outside the stream; the guest records the skipped IDs as tombstones (`SkippedIds`) and tolerates later commands naming those host-only PCs. The host's own canonical IDs must start exactly at its allocator.
- [`NativePcLifecycle`](../../src/PCBS2Coop.Plugin/NativePcLifecycle.cs) intercepts the three user-intent boundaries above (the case branch only when the native switch would proceed). The requesting peer runs the same native steps after acceptance (`Projecting` lets them through the 3d guards); the other peer keeps a mod-held remote carrier record (no mesh until 3f) or removes its own projection. UI state stays local: the inventory closes only if the state at request time is still current; a refused storage delete runs the game's own "No". A guest waits for each answer before another request.
- Guest re-admission with its own logically carried PC no longer puts that record in the native save's carry slot: after admission it is spawned through `PickupComputerFromStorage` (E3 below). Stale spawn tickets are dropped once the world has settled with nothing loading.
- Interim gap accepted by the owner: a guest that places or stores its spawned case natively is still recorded as carrying it, so the host refuses its next spawn ("Your hands already hold a PC."). The other player doesn't see spawned/moved PCs until 3f. Absent-carrier departure recovery is still governed by 3f.

### Implementation contracts

- [`PcTransfers`](../../src/PCBS2Coop.Network/PcTransfer.cs) (command type 4) is a host-ordered handler with five actions:

  | Action | Names |
  | --- | --- |
  | Pickup | the PC and the bench it was seen on |
  | Drop | the carried PC, the bench, and the occupant the requester saw (none, or a deliberate swap) |
  | Store | the PC |
  | Retrieve | the PC |
  | Recover (host only) | a departed seat |

  - The host checks the actor epoch, the source location, the destination and the activity of every moved PC, then the host-native preconditions. A valid destination is empty hands, an empty or unchanged bench, or the cupboard.
  - Every accepted transfer changes all affected locations in one `ObjectWorld.Replace`, so a PC never has two locations or none. A swap lists its bench side first.

  - The requester's game runs the native call after acceptance. The host's own requests resolve within the same call.
  - The other game projects the accepted move without touching its own carry singleton or UI:

    | Move | Projection on the other game |
    | --- | --- |
    | bench → hands | runs `Case.OnPickup`, saves the record, calls `DestroyComputer` |
    | cupboard → hands | removes that record |
    | hands → bench | loads the held record through `LoadComputerToSlot` with a bound load ticket |
    | hands → cupboard | appends the record |

  - Open storage views repopulate.
  - A local work or monitor view of a PC the other player takes is exited first. This covers the race with a work entry that is still in flight.

For a local gesture `DropPC` repeats this afterwards, which changes nothing.
- A load that completes records its native operation key. On the next main-thread update, before the readiness barrier, the adapter removes only those completed records from `m_loadPCOperations`; a load whose attempt is still open is left alone.
- [`NativeProjection`](../../src/PCBS2Coop.Plugin/NativeProjection.cs) is the shared "accepted change is running" flag for 3e and 3f. When a native drop inside a projection triggers a Free Build autosave, the save is deferred to the next frame. A host save captures and may submit changes, which isn't allowed inside `Apply`. On the host the deferred save waits until the world is ready, so it isn't lost on a frame where the save would be refused.

### Implementation contracts

- [`WorkstationWorld`](../../src/PCBS2Coop.Network/Workstations.cs) (command type 5, world state `workstations`) holds one fact per slot: bench ID, position in that bench's slot array, and the installed asset path (empty for an empty slot). A swap names the requester's epoch, the slot, the path it saw and the catalog part ID.
  - The host refuses an unknown slot, a stale "seen" path ("That peripheral was just changed."), a part whose type doesn't match the slot or that the slot's `IsCompatible` rejects (a mouse pad too large for its desk), a stale epoch, and a swap at a workstation where the other player works on a PC on its main or tool bench. The requester's own work there doesn't block it. The host's native check refuses while that slot is still loading.
  - The host canonicalizes the part to its asset path. Each peer re-checks the change against its own copy and its own resolution of the part, and diverges explicitly on any difference.
  - The host binds the facts from its loaded world at every generation start. A paired save or snapshot carries them, and the loaded world must match them exactly (host restore and guest admission). The state is optional when restoring: a 0.8/0.9 paired save has none and is bound from the world. `CoopSavePair` reads those two older versions; their layout is otherwise unchanged.
- [`NativeWorkstations`](../../src/PCBS2Coop.Plugin/NativeWorkstations.cs) intercepts `SwapPerif` on the base slot and the five overrides, hooking each distinct native function once ([`GamePatches.NativeCode`](../../src/PCBS2Coop.Plugin/GamePatches.cs)): a second hook on the same code crashed the game when the original ran (G2). The prefix may receive any of the merged slot types, so it uses only `PeripheralSlot` members. Plugin startup logs an error if any two patched methods share native code; the probe skips such observers. After acceptance the requester runs the same native swap with its chosen part; the other game runs it for the same slot with its catalog entry (or a fresh instance of that part). One native swap runs at a time per slot: a swap accepted while the slot is still loading waits, and the latest accepted fact wins. Peripheral selection, inventory browsing and the install UI stay local. Guests keep one outstanding request across PC creation, transfers and swaps.
- Host saves and snapshots require the game to show exactly the accepted peripherals; a snapshot waits until no swap is loading. World readiness also waits for first peripheral spawns (at most 30 s, then it logs and stops waiting; the binding check then reports a mismatch).
- Packages and physical notes: a world containing a package, a slotted note, or a carried package or note is refused. The host returns to the menu with the reason before starting a world generation; host saves and snapshots fail with the reason (replacing 3c's carried-only check); a guest never enters such a world.
- Not covered here: LED configuration (RGB, phase 11), peripheral cables, plugs and power (phase 5), monitor/screen and virtual-computer state (phase 6), and bench tools (`BenchToolSaveList`, specialist/3h).
