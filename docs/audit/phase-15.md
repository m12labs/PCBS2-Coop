- Both players share one host-owned run, wallet, owned inventory, jobs and progression. Either player may act on that shared state with host validation. The host controls day advancement and workshop/load transitions.

## Shared command pipeline

Use `WorldSync` for ordering, admission, operation IDs, generation checks and registered state. Register typed Career commands and snapshot state alongside existing handlers in `CoopController.OnWorldCreated`. Keep save serialization and native projection on the game thread. The scope of a command is one logical operation such as buying an order, collecting a job or advancing a day. Use stable references to inventory, PCs, jobs, offers and the day where the action depends on them. [WorldSync](../../src/PCBS2Coop.Network/WorldSync.cs) · [Controller registrations](../../src/PCBS2Coop.Plugin/CoopController.cs#L746)

Intercept each native action before its first irreversible write. Submit intent with the relevant expected facts and actor epoch. The host checks legality and conflicts. Use the existing activity/claim system for PCs and reserve other affected resources for asynchronous operations. Project accepted facts under `NativeProjection.Run`; callbacks that cross frames need an explicit generation/operation check. If a host-native action must resolve an outcome asynchronously, order the begin/reservation and the canonical result as separate steps. Do not start another command, run a save or finalize an uncertain native outcome from inside `Apply`. Freeze capture/admission at unsettled boundaries and report projection errors through the existing recovery path. [Projection guard](../../src/PCBS2Coop.Plugin/NativeProjection.cs)

Hooking `SpendCash`, `AddCash` or a generic inventory writer alone loses context about which order, job or transfer changed the balance. Those are useful projection and diagnostic points. Keep entry hooks thin and let the shared handlers validate each operation's full effects. Verify hook aliases against real generated interop before patching.
