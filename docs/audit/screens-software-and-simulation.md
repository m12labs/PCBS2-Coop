# Screens, software, and PC simulation sync audit

Scope is virtual PC software, screen presentation, benchmarks, simulation and tablet surfaces in the decompiled `Assembly-CSharp`. The audit is source inspection only; no game runtime behavior was verified. C# files here are metadata declarations with placeholder method bodies. I use those files to establish field/signature shape, and native ISIL for the limited behavior claims that it actually exposes. A class or minigame type in the decompile does not prove that it is installed, reachable, enabled, or shipped in the current build.

The plugin currently sends only workshop player position, yaw, and an `InWorkshop` flag (`src/PCBS2Coop.Network/Protocol.cs`, `PlayerState`; `src/PCBS2Coop.Plugin/CoopController.cs`, `Find`/`Update`). None of the objects below appear in the plugin's sync path. Each row therefore records current sync as **Missing**. “Candidate” means a plausible representation if a future coop mode shares the virtual computer; it is not a policy recommendation. Owner decision remains pending for which PC, software, screen, app, or simulation state becomes shared.

## Cross-cutting classification

- **Shared underlying state candidates** include computer/save identity, installed software/file state, BIOS config, hardware configuration selected elsewhere, app-owned durable data (if selected), test/run identity and authoritative terminal outcomes. These are candidates only; owner policy is pending.
- **Derived presentation candidates** include monitor/desktop pixels, boot progress, BSOD art/text, app window layout, taskbar, cursors, graph pixels, thermal/airflow overlays, LCD readouts, animations, GIF/video frames and tablet render feeds. If the world is shared, these should be rendered locally from selected state where feasible; pixels alone omit causes, semantics and reconnect state.
- **Local-pending candidates** include OS window focus and pointer, monitor resolution/camera bindings, local render textures, tablet orientation/camera routing, audio output/volume, user file paths and custom image bytes. Their sharing is a product/design choice, with privacy and cross-machine asset questions still open.
- **Identity and ownership remain unresolved**: no stable virtual-computer network ID or shared-session authority is present in current protocol. Workshop scene object identity may differ per client. Concurrent app input can mutate software, BIOS, benchmark result, notes and simulation. Any shared surface needs an explicit owner/command ordering and late-join snapshot before incremental sync design.
