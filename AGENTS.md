# Agent instructions

PCBS2 Coop is a BepInEx 6 IL2CPP multiplayer mod for PC Building Simulator 2 (Unity 6000.2.6f2, Windows x64). Two players share one Free Build workshop over LAN or Steam. The host picks New Game, Continue or Load Game in the Co-op menu. A guest joins from the host's current snapshot. Co-op worlds use `Saves\Coop` and the host's native save plus a `.coop` sidecar.

Use [the sync tracker](docs/sync-progress.md) for current feature status, [the two-game checklist](docs/needs_testing.md) for gameplay acceptance and [the roadmap](plan.md) for phase closure. Version 0.57 closes the applicable Free Build gameplay checklist. Phase 13 covers remote presentation. Phase 14 (release completeness, faults, performance and two-machine validation) is skipped for now. Career began at phase 15: 0.58 adds Host Career, mode-aware saves and admission. 0.59 shares the host's career numbers, ledger and owned items. 0.60 shares shop carts, checkout and part sales (none run in game yet).

Free Build currently shares the supported PC, bench and inventory changes, building, cabling and power, water cooling, boot/BIOS and installed programs, tuning and failures, tool results, workshop customization and save/rejoin. Cleaning is deferred to Career. The game build has no reachable LED strip tool. Co-op refuses worlds with physical packages or notes. Read the relevant phase audit before changing native behavior.

## Layout

| Path | What it is |
| --- | --- |
| `src/PCBS2Coop.Network` | Unity-free layer over LiteNetLib 2.1.4: `CoopSession` (one host, one guest, identity handshake, guest admission), `Compatibility` (refuse a different mod version or game build, warn DLC/catalog), `WorldSync` (host-ordered world changes, snapshot position, hold/replay), `WorldTransfer` (chunked, hashed snapshots), `Identity` + `ObjectRegistry` (player/operation/object IDs), `ObjectWorld` (PC/part facts, locations, allocator, tombstones), `ActorActivity` (per-player work/claims), `PcLifecycle` (host-ordered PC create/delete, host observation and load growth), `PcTransfers` (host-ordered atomic pickup/drop/swap/store/retrieve and departure recovery), `WorkstationWorld` (host-ordered peripheral swaps per workstation slot), `MechanismWorld`/`CasePanelWorld` (latches, case panels), `ComponentEditWorld` (component edits), `CoopSavePair` (native save + `.coop` sidecar), `Protocol` (message types, limits) |
| `src/PCBS2Coop.Plugin` | BepInEx plugin (`PCBS2Coop.dll`): `CoopRunner` main-thread driver, `CoopMenu` (the co-op list swapped in on the main menu) + `CoopDialog` popups, `CoopController` session/world lifecycle/snapshots/remote view, `CoopSaves` co-op save folders, `WorldReadiness` load barrier, `GamePatches` (save/load/object/activity hooks), `NativeObjectState` (native PC binding/capture), `NativeActivity`, `NativePcLifecycle` (spawn/delete interception and projection), `NativePcTransfers` (transfer interception, local and remote projection), `NativeWorkstations` (peripheral swap interception/projection, package/note refusal), `NativeProjection` (accepted-change flag), `CoopAutosave` (when the host saves a co-op world; the game's autosaves are skipped), `GameInfo` local identity, `WorldHandlers`, `RemotePlayerView` capsule + name tag + carried-PC box, `Diagnostics` census, `AutoTest`, `Probe` (audit probe, `PCBS2COOP_PROBE=1` with the self test) |
| `tests/PCBS2Coop.Network.Tests` | Network acceptance tests (`dotnet run`): identity/compatibility, in-memory fault injection for `WorldSync`, admission and snapshot transfer, UDP loopback sessions |
| `scripts/*-Phase3Probe.ps1`, `scripts/Test-Phase3Reload.ps1` | Opt-in owned game runs and edited-save regression; `Phase3Probe` requires self-test isolation plus `PCBS2COOP_PROBE=3`. Commands and evidence: `docs/audit/phase-3.md`. |
| `scripts/Install-Loader.ps1` / `Uninstall-Loader.ps1` | Install BepInEx be.791 into the game with a rollback manifest in `.local/` |

## Build and test

```powershell
dotnet run --project tests/PCBS2Coop.Network.Tests -c Release   # network loopback test
dotnet build PCBS2Coop.sln -c Release                           # builds and copies the plugin into <GameDir>\BepInEx\plugins\PCBS2Coop
```

No machine-specific path is committed. Set your game folder once: copy `Directory.Build.local.props.example` to `Directory.Build.local.props` (git-ignored) and fill in `GameDir`, or set `PCBS2_GAME_DIR`, or pass `-p:GameDir=...`. The PowerShell scripts read the same file/variables (`scripts/LocalPaths.ps1`; `GhidraHome`/`GHIDRA_HOME` and `Cpp2ILPath`/`CPP2IL_PATH` for the decompile tools). Never write a real local path into tracked files, docs or commit messages; use `<GameDir>`. The deploy copy can't replace the DLLs while the game is running (they are locked), even when the build prints "Deployed"; close the game, rebuild, and compare the deployed `PCBS2Coop.dll` with `bin/Release` before a test run. Build against the real `BepInEx/interop` generated by a first launch, never against the decompiled dummy DLLs.

### Two-instance self test

Set `PCBS2COOP_AUTOTEST=host` for one launch of `PCBS2.exe` and `=join` for a second (working directory `<GameDir>`). Each instance first redirects the game's save folder to a fresh `BepInEx\PCBS2Coop-diag\saves-<role>` (the owner's `Saves` folder is never used; an overwrite prompt is only auto-accepted inside that folder) and clicks with real pointer events. Round 1: host → Co-op → Host Co-op → New Game → Start, three markers; guest joins ~30 s later and loads the host's world (the host adds one marker while it loads); both aim at the other's capsule and screenshot; five markers each (guest also one invalid); host pauses, then saves (guest must get the copy); `AUTOTEST: world summary …` and `PASSED/FAILED` on both (summaries must match); host leaves, guest must return to the menu with the reason. Round 2: host → Host Co-op → Continue, guest rejoins, guest leaves first, host keeps hosting. Each side ends with `AUTOTEST: finished.` (about two minutes). Census files and screenshots go to `<GameDir>\BepInEx\PCBS2Coop-diag\`. Logs: `BepInEx\LogOutput.log` (first instance) and `LogOutput.1.log` (second). Normal launches never run this. `PCBS2COOP_DIAG=1` writes census files without the self test.

## Versioning

`<Version>` in `Directory.Build.props` sets the plugin version, the network assembly version and the join check. Two players must use the same version. Bump it whenever a build changes network or co-op save data and before handing a build to someone. A co-op save loads under its writing version and later versions that list it in `CoopSavePair.SameFormat`.

- Each bump adds one to the number after the dot: 0.1, 0.2, 0.3, 0.4, … (0.9 is followed by 0.10).
- BepInEx shows it with a third part (0.3 → `0.3.0`). Only an exact match matters for joining.

## Findings the code depends on

- Main menu: `MainMenuHUD/NewMainMenu/MainMenu/Button2-FreeBuild` has sub-buttons `ContinueFreebuild`, `LoadGame`, `NewGame`. Their actions are attached to each sub-button's `Button.onClick` at runtime, so `Instantiate` copies don't inherit them. The `CustomEventTrigger` on them has no entries.
- The menu activates panels one at a time while fading in; a cloned panel must follow the source's active state and `CanvasGroup` alpha. A single-click entry (Options, Quit) runs a serialized `IndividualMenuButton.OnClick("<NewMainMenu method>")`, which fades every panel and then `SendMessage`s that method: replace a clone's `Button.onClick` (`Ui.ReplaceClick`). `MenuExtras` (social icons, news) is a child of `MainMenu`. The co-op list is a sibling container; each list is hidden by a `CanvasGroup` on its container, so the game's own panel fades can't show it.
- Free Build save names: `FreebuildSave`/`SaveCurrentGame` always write `s_autoFreeBuildSaveName` (`autofreebuild.binary`); the Save screen writes `<typed name>.binary` with the typed name as the header's `m_saveName` (`CreateSaveGame`'s `OverrideName`). The load list labels a file starting with `auto` as "Autosave", else shows `m_saveName`, else the file name; its Free Build list hides `defaultFreebuild`. Co-op redirects the autosave per world in the `CreateSaveGame` prefix (`CoopSaves.RedirectAutosave`, names in `CoopWorldNames`). A `.coop` pair loads only under a mod version that reads its format (`CoopSavePair.Readable`).
- Game autosaves (decompile): `FreebuildSave` is called by `WalkingState.OnStateEnter` (leaving work mode, so after every edit), `WorkshopController.DropCase`, `DecorationSwitch.OnClickSwitch`, `WalkingState.WaitForLoad` and, through `SaveCurrentGame`, `NewLoadingScreen.LoadASync` after a workshop scene loads. The game doesn't save on Exit (`ExitPanel.Exit` only loads `Main_Menu`). In co-op every `FreebuildSave` is skipped on both games (owner decision, 0.17); the host's interval, Exit and `/sync` saves call `CreateSaveGame(s_autoFreeBuildSaveName)` directly, and the Save screen (`SaveLoadMenu.WriteSave`) calls `CreateSaveGame` itself.
- `NewMainMenu.PlayFree()` starts a new Free Build in scene `Stage_02_Workshop`. If a Free Build save exists it first shows `MessageBox.Show("New Game", ...)`.
- Workshop player: root `Player` (`CharacterController`, `Walk`) with child `Main Camera` (`MouseLook`).
- HDRP: Unity's default primitive material doesn't render. Copy an `HDRP/Lit` material already in the scene.
- Unity 6 interop `CoreModule` exports its own `NullableAttribute`, so the plugin project builds with `<Nullable>disable</Nullable>`. Lambdas taking parameters from nullable-annotated Network events need explicit parameter types.
- Unity 6 interop wrappers that pass strings or arrays through `ManagedSpanWrapper` (e.g. `AssetBundle.LoadAsset`, `LoadAllAssets`, `LoadFromMemory`) throw `MissingMethodException` for `Il2CppSystem.ReadOnlySpan.GetPinnableReference` in game. `AssetBundle.LoadFromFile` and `LoadAssetAsync(name, type).asset` are plain native calls (see `PlayerModelAssets`). Check a new Unity API's interop body for `GetPinnableReference` before relying on it.
- `Input.inputString` is stripped. TMP input fields work through the game's `InputModule`.
- Saves: `SaveLoadSystem.s_saveDir` is the relative path `Saves`, i.e. `<GameDir>\Saves`, shared by every local instance. Redirecting `s_saveDir` on the main menu also redirects PlayFree's existing-save check (run R1). The game lists only the top level of that folder. Saves are `<name>.binary.zip` with one `<name>.binary` entry.
- `CreateSaveGame(name)` fixes the target path at call time (safe to restore `s_saveDir` right after), writes on a thread (`WaitingOnThread()`), and makes that file the game's current save name (`LevelLoadPersistency.SaveName`, `SetOpenedSaveName`): restore both after a side save. Every save path goes through it; Harmony hooks on it fire for native callers.
- Load an exact co-op save through `CoopController.LoadNamedFreeBuild`: set `LevelLoadPersistency.gameModeToLoad = FREEBUILD`, then `LoadGameFromDir(name, Stage_02_Workshop, false)` (name = the save list's `m_name`, e.g. `coopworld.binary`). `NewMainMenu.ContinueFreeBuild(string)` uses only the string's emptiness and prefers the default build for a nonempty value; it does not select that filename. Verified with an edited-world reload in phase 3b; see `docs/audit/phase-3.md`. A new Free Build uses the shipped `StreamingAssets/UtilitySaves/defaultFreebuild.binary` copied into the co-op folder.
- `NewLoadingScreen.LoadScene("Main_Menu", false)` returns to a working main menu. Pause only sets `GameController.paused`; `Time.timeScale` stays 1 and `Application.runInBackground` is already on.
- Players spawn at the player position stored in the save, so a joining guest starts where the host's save placed the player.
- Identity: `Application.version` is just `0.1`; the build GUID comes from `PCBS2_Data\boot.config`. The part catalog (`PartsDatabase.s_instance.m_parts`, 2816 parts) is already loaded on the main menu. Parts, PCs and benches have no instance IDs in game data; the mod assigns `NetObjectId`s.
- The game has its own global type named `Compatibility`; use `PCBS2Coop.Network.Compatibility` in the plugin.
- The game's linker merges identical method bodies, so different IL2CPP methods can share one native function. Hook each native function through one method only (`GamePatches.NativeCode`): a second hook on the same code crashed the game in the .NET runtime when the original ran (3g, G2). Startup logs `[hooks]` errors for any such pair.
- LiteNetLib 2.1.4 throws `InvalidOperationException` on short reads; parsers use `Protocol.IsReadError`. Don't use `PutBytesWithLength`; use `Protocol.WriteBlob`/`ReadBlob`.

## Synchronization contracts (phase 1)

- The host orders every world change. Guests submit requests through `Session.World.Submit`; a change takes effect on both peers only when the host's confirmed `Mutation` arrives. Register one `ICommandHandler` per command type in `CoopController.OnWorldCreated`.
- `Validate` runs on the host only. `Apply` runs on both peers in revision order on the main thread; it must make the change only, never trigger game paths that submit another change.
- A world generation is one incarnation of the world (host starts it with `BeginGeneration`, never from inside `Apply`). Requests/changes from another generation are refused or dropped.
- Remote players' activity is per-actor data. Never write it into `GameController`/`WorkshopController` singleton fields.
- Details and evidence: `docs/audit/phase-1.md`.

## World lifecycle contracts (phase 2)

- A joined guest is not in the world until it loads a host snapshot (`CoopSession.GuestNeedsWorld` → `BeginSnapshot` in the same frame as the game save → `SetSnapshotFile`; guest `SnapshotReceived` → load → `CompleteAdmission`). World changes after the snapshot mark are held and applied after the load. Mod-side state a late joiner needs goes in an `IWorldState` registered on the world.
- The host starts a world generation only when its world is ready (`WorldReadiness`). A guest that receives a new generation after admission leaves to the menu.
- While a co-op world is loaded, `s_saveDir` points into `<saves>/Coop` (host: `Coop`; guest: `Coop/GuestSession`, copies in `Coop/Joined`); it is restored only on the main menu (`CoopSaves`).
- No shared pause: nothing in the session may depend on the game's pause flag.
- Details and evidence: `docs/audit/phase-2.md`.

For acceptance follow-up and the 0.25 admission fix, read `docs/audit/acceptance-2026-11-04.md`. A load stays pending after its bytes enter the transport until the guest acknowledges receipt; Loading names the snapshot's generation. The owned 39-built-PC save/join/`/sync`/Continue case passed; other unchecked cases in `docs/needs_testing.md` remain open. Steam is owner-confirmed complete. Phase 6 `-Resume` skips old command history; append new commands only after this process's readiness evidence, using `Send-Phase6ProbeCommand.ps1`.

For object binding, canonical command payloads or co-op save changes, read `docs/audit/phase-3.md` task 3c. Co-op saves require their hash-matched `.coop` sidecar; native-only co-op saves fail explicitly. Logical part IDs are scoped to their PC and native field/slot graph, with aliases preserved inside that graph. Use `BenchSlot.GetComputer`; the installed interop loses `GetComputerRef`'s native reference return.

For activity, operation claims or movement guards, read task 3d in `docs/audit/phase-3.md`. Validate actor epochs and acquisition tokens through `ActivityWorld`; claim dependency resources together. Guard the outer native interaction: `BenchSlot.OnPickupPC` clears its slot even when its downstream `PickUpCase` is refused. Version 0.5 adds session activity to paired saves; older co-op formats require phase 8 migration.

For PC creation/removal, read task 3e in `docs/audit/phase-3.md`. Free Build catalog entries are reusable templates: a case spawn builds `new ComputerSave { caseID = item }` and only replaces an empty carried case; in-world delete is `AddCaseToInventory` → `DestroyCarriedCase`; the confirmed storage delete is `StoredPC.DeletePC`. Never poll `BenchSlot.GetComputer(true)` or `GetCarriedComputer()`: both re-run `SaveComputer`. Version 0.8 includes prefab default fans in the creation template; use `PcLifecycle.Extend` for older/unpredicted pure load growth before host capture. A guest's own carried PC is restored after admission through `PickupComputerFromStorage`, not the native save's carry slot. Version 0.6 changes wire/save state.

For PC transfers, read task 3f in `docs/audit/phase-3.md`. Intercept the outer gesture, not `PickUpCase`: `BenchSlot.OnPickupPC` and the tool-bench closures `BenchToolSlot.__c__DisplayClass37_0._PopulateToolActions_b__4/5` clear their slot after `PickUpCase`. Every drop and swap goes through `WorkshopController.DropCase`; store is `StoreCarriedCase`; retrieval is `StoredPC.PickUp`. Run an accepted change's native calls inside `NativeProjection.Run`. A host save must never run inside `Apply`; the Free Build autosave a drop triggers is skipped like every game autosave in co-op (`CoopAutosave`). The other game never writes its carry singleton:
- bench → hands: `Case.OnPickup`, `GetComputer(true)`, `DestroyComputer`
- hands → bench: `LoadComputerToSlot` with a bound ticket
- the cupboard: `computersInStorage` (remove or append), then repopulate the open storage views

A carried PC of the other player is a box derived from the model. Version 0.7 adds command type 4. Version 0.8 includes prefab default fans in creation before allocating IDs, so guest-created PCs can go straight to storage. Read the actual Addressables case asset; GetPrefab may return a placeholder before the first spawn. A remote bench load keeps an untouched carried record and uses a separate native input graph. A later pickup cancels the attempt; the LoadComputerToSlotAsync prefix checks the ticket before native placement. Use explicit capture boundaries to check native graphs; the load input record temporarily splits water-loop aliases. Completion callbacks only bind/clean up and never re-save a PC for diagnostics. A load whose parts are all cached finishes before `InitComputerLoading` queues it, which leaves an orphaned `m_loadPCOperations` record; completed records are cleared on the next update. `BenchSlot.OnPickupPC` hides a workbench slot that only `BenchSlot.DropPC` shows again. Any PC the mod places on a bench (`DropCase`, `LoadComputerToSlot`) must go through `NativeObjectState.ShowBench`. Otherwise it is invisible and saves water pipes without their parts, and the game can't load that save. Runtime evidence and remaining specialist/failure cases are in task 3f.

For workstation peripherals, packages and notes, read task 3g in `docs/audit/phase-3.md`. A peripheral slot is the game's bench ID plus its position in `SaveLoadSystem.GetBenchPerifSlots()`; its fact is `Peripheral.AssetPath` (what the native save writes). Intercept `SwapPerif` on `PeripheralSlot` and the five overrides, hooking each native function once (the headset, keyboard and mouse overrides are one function); `Swap` installs a part only if its `m_type` is a peripheral type equal to the slot's `Type`. The base `IsCompatible` always returns true, but `MousePadPerifSlot.SwapPerif` silently skips a pad its `IsCompatible` rejects (pad size vs. the desk), so validation checks it too. Run one native swap per slot at a time; a swap accepted while the slot loads waits. The `workstations` state is optional on restore (0.8/0.9 saves lack it) and the host rebinds it from the loaded world at every generation start; a loaded world must match a restored state exactly. A world with a package, a slotted note or a carried package/note is refused (owner decision): never save, send or enter one.

For chat and `/sync`, read task 3h in `docs/audit/phase-3.md`. Chat (message 12) and sync control (message 13) are session messages, not world commands. A sync keeps the session open through the main menu (`CoopController.OnMainMenu` returns early while it runs): the guest leaves the world with `WorldSync.LeaveWorld` (state `GuestState.Leaving`) and asks for the world again from its menu; the host saves (its own game is the reference, so peripherals are rebound rather than checked), continues that exact save and starts a new generation. No snapshot is sent while a host sync runs. While the chat input is open, Rewired's keyboard and mouse controllers are disabled so the game ignores the keys. "Out of sync" means a divergence, an adapter-caught projection failure (report it with `CoopController.ProjectionFailed`, never only a notice), or a projection ticket older than the settle period + 3 s while the world is ready (`NativeObjectState.ProjectionFault`; younger tickets may come from a load started this frame). Before the `/sync` save, `NativeObjectState.RecoverUnshown` puts any accepted PC the host's game isn't showing into the cupboard; otherwise the capture would retire it. A remote bench drop loads with `loadCables: true` (false also drops internal cables), which plugs the bench's external cables in; once the world settles, `NativeObjectState.SettleRemoteDrops` runs `Case.OnPickup`, `EnableCaseColliders(true)` and `OnPutDown(bench)` so it ends "Not plugged in" like the mover's own drop.

For latches, read task 4d in `docs/audit/phase-4.md`. The player's latch click is `PinTick` on `WorkingOnComputerState` or `LayCableState` (directly, or its `DoAfterLongPress` callback); only a `TogglePin` inside that gesture becomes a host-ordered request (command 7). The game's own toggles (an install closing clips, a load closing clips over installed RAM) pass through. `TogglePin` silently does nothing while a latch is blocked or animating, so let such a call run. Show an accepted toggle with the native toggle, or `PopOpen`/`Pin.Close` where only this game blocks it. A pending or moving latch blocks capture (`NativeAssembly.CanCapture`). Clips over installed sticks are live-only (owner decision): `SettleForCapture` closes them before every host save/snapshot, and a PC leaving its bench settles them in the model (`AssemblyResource.LoadCloses`). Case panels (command 8, `NativeCaseAccess`) are integral `CASE_PART_*` slots with `IntegralHome`; what a panel carries stays in the model while it is off (dormant) and paths inside a fitted panel use `@panel` (a refitted panel is renamed after its prefab). The requester replays the game's long-press callback; the other game changes the panel directly (load-path instantiation / teardown), and the PC is rebound only after the native result shows. Every other `DisassemblyTick`/`AssemblyTick` long press is a component edit (4e); water-pipe removal stays refused. Never put `Slot.m_dynamicBlockedBy`/`m_dynamicComponentCollidesWith` in the manifest: they are live caches filled after work mode.

For component installs and removals, read task 4e in `docs/audit/phase-4.md`. Command 9 (`ComponentEditWorld`):
- `Begin` (editor): the host checks the slot and its own game and claims the PC.
- The editor's stored long-press callback runs the game's own edit (`NativeComponentEdits`).
- `Progress` (editor, part edits only, 0.17): `Started` once its game began the edit (an install sends the part's inventory source and flip), then `PartStep` when a removal passes its cable step. The other game starts its detached replay (`NativeEditReplay`: never `SetCurrentState`, guards inert outside a replay step) on `Started`; a removal waits after its cable step until `PartStep` or the commit.
- `Commit` (editor): what the editor's game ended with. A running replay waits at the orientation step and before settling until it arrives (`Plan.Known`); without a running replay the other game replays the whole edit then.
- `Settle` (host, once its own game shows the result): the captured PC. Parts keep IDs by native instance and resources by binding.
- `Cancel`: the editor drops an edit that never ran; the host drops one it can't settle.

While another actor's edit claim is pending on a PC, latches, panels and edits on that PC are refused (owner decision). `DisassemblyTick` b__0 is a placeholder install, b__1 the direct removal, b__2 the `Uninstall` coroutine. Never hook `SetCurrentState`, `OnStateDestroy` or the replay targets through a second method that shares their native code.

- The native install and load paths parent generated `Standoff(Clone)` screws differently. Bind these motherboard mounts by their order in motherboard space. On load, 0.48 translates old generated-standoff bindings before publishing the registry, keeping their IDs and links. Prefab screws keep their original paths.

For cables and power, read `docs/audit/phase-5.md`. They are command 9 gestures `Connect`, `Unplug` and `Power`, each with a whole-PC edit claim (no targets):
- The editor's gesture is the cabling long press `<CablingTick>b__0` (its `ConnectCableState` may install a splitter on entry), the unplug long press `<RemoveCableTick>b__0`, `PowerButton.Press`, `WorkingOnComputerStateBase.PowerClicked`, or a walking bench power callback (`BenchSlot.<GetInteractions>b__8/9/10`, 0.26). Only Power can claim a PC while walking.
- The walking monitor's P prompt comes from `InteractableComputer.GetInteractions` and has its own on/off callbacks (shared in 0.44).
- The editor is followed until nothing moves on that PC. The commit carries a `Wiring` change: cables off/on, splitter/adapter slots, inventory and power.
- The other game applies that change with the game's own calls (`NativeComponentEdits.Wiring.cs`).
- The guest may receive Settle before its cable replay starts or finishes. Assembly rebind waits for `WireMoving` on that PC, including a queued replay (0.29).
- `PcFact.Powered` is bench-only (`PcFact.At` clears it on a move). The game doesn't save power, so each game turns powered PCs on again shortly after a load.

For custom water cooling, read `docs/audit/phase-10.md`. It is command 9 gesture `Water` (whole-PC claim). Gestures: `<PipingTick>b__0`, `<DisassemblyTick>b__3`, `WaterLoopController.FillLoop`/`EmptyLoop`, and 4e installs/removals of water parts and slots. The editor sends its finished PC record in `Chunk` steps before the commit. The other game reloads that PC (`NativeObjectState.ReloadOnBench`), and the host captures part IDs by path.

- A piped cooler can occupy multiple radiator slots and a CPU slot through `ComponentPC` proxies. From 0.47 the removal callback resolves a proxy to its piped owner, checks that the main slot can be uninstalled and removes the entire assembly through `Water`. Removing only the proxy leaves radiator and pipe entries that native Continue cannot restore.

For BIOS, desktop and software (phase 6), read `docs/audit/phase-6.md` "Mirrored desktop input":
- Command 13 `PcRepair`: a guest that can't show an edit (or rebind a PC) reloads that PC from the host's record with a notice (`NativePcRepair`); the host never repairs, its game is the reference. Edit replays need a camera even when `Camera.main` is null (player at a monitor).
- Command 10 `Bios` (Apply/Factory Reset), command 11 `DesktopInput` (mirrored input batches; the sender's own game already ran them, so `Apply` skips the local actor), command 12 `Software` (host boot-drive records; the guest adopts the host's when they still differ after both settle).
- Coordinates are fractions of the PC screen's root canvas. The OS canvas is world-space and its event camera is whoever looks at it: replays use a disabled helper camera in front of the screen, set as the canvas camera only during the replayed event, and skip `VirtualComputer.m_screenBlocker`. Give the EventSystem selection back after a replay; never write the remote cursor into `InputModule`.
- `IsPoweredOn()` is false while the BIOS is open: check `IsInBios()` first. Desktop icons open on a double click.
- Replayed native code runs with `NativeDesktopInput.Injecting` inside `NativeProjection`; hooks that turn a click into a request must ignore replayed clicks.
- BIOS entry on the other game: `_StartupSequence_d__69.MoveNext` with the BIOS key forced held (`NativeEditReplay.InputGuard`) and a stand-in `LookingAtMonitorState` as `GameController.m_currentState`.
- A cold co-op load can start boot before Rewired has a last active controller. From 0.27, the BIOS prompt's atlas and text formatting calls can recover from a native null reference within a co-op boot step. Boot and BIOS input continue and the prompt can be blank for that boot. The guest still has the one-restart fallback when the host reports its desktop.
- Phase 6 probe: `scripts/Start-Phase6Probe.ps1`/`Stop-Phase6Probe.ps1`; `commands.txt` beside `events.jsonl` takes `aim:<bench|peripheral>:<n>`, `desktop-report`, `screen-dump:<pc>`. Wait for this run's own `pc-bindings` event, not log text (the log still holds the previous run). No in-game screenshots (GPU watchdog incidents); use Windows-level screenshots.

For saves, backups and rejoin (phase 8), read `docs/audit/phase-8.md`:
- The world state is compressed on the wire (snapshot mark) and on disk (sidecar layout `PC2PAIR2`): `Protocol.PackState`/`UnpackState`, 16 MB expanded and 1 MB packed. 0.21 still reads the uncompressed 0.16–0.20 layout.
- Before every host save into `Saves\Coop`, `CoopSaves.KeepBackup` copies the pair about to be overwritten to `Saves\Coop\Backup` if it still reads (`CoopSaveBackups`). The main menu, Continue, Load and a pause-menu Load put a backup back in place of a save that doesn't read; Continue takes the newest save that reads.
- Pause menu: the host's `SaveLoadMenu.OnLoadSelected` and `LevelLoadPersistency.ResetFreebuild` become a world switch on the `/sync` path (`StartWorldSwitch`). A guest's `NewSaveGame`, `OverwriteSave`, Load, Reset and every `CreateSaveGame` are refused. Never let a workshop reload run outside a new generation.
- Rejoin: a guest leaving unexpectedly gets Rejoin (same LAN address/port or Steam lobby). Session message 14 `Spawn` (host → admitted guest) gives where that player stood; the host remembers it per player while the world is loaded (`CoopRejoin.cs`).
- `SaveLoadMenu.NewSaveGame` and `OverwriteSave` are one native function: hook `NewSaveGame` only. The Save screen's overwrite names a save by its header (display) name; `CoopSaves.RedirectShownName` maps it back to the file.
- What a fresh load doesn't rebuild must not be recorded as shared structure: `Slot.DynamicMustBeOpenPins`/`DynamicClosePins` (like `m_dynamicBlockedBy`) are left out, and the inventory binding (`v2:`) skips removed case panels (`Case_SKU/Panel` entries the game's save drops). `Slot.blockedBy` differs by path (the game's own gesture adds neighbours' blockers; a replay or a fresh load doesn't), so slot blocker lists aren't compared on the other game (owner decision, Nov 2, 2026).
- Phase 8 probe (phase 6 probe commands): `summary-report`, `pose`, `save`, `world-load:<name>`, `world-reset`, `saves-report`, `dialog-report`, `exit`, `chat:<text>`; `Start-Phase6Probe.ps1 -Resume` relaunches a host on its run's saves and presses Continue. A relaunched game needs one real mouse click before it loads a world, or a PC that was on stays on its boot screen (`JobTutorialHintUi` reads Rewired's last active controller). A dropped connection: suspend one game's process for about 12 s.

For simulation outcomes (phase 7), read `docs/audit/phase-7.md`:
- Each game simulates every powered PC itself (`ComputerSim`); nothing of it is saved. Failure times are pure functions of the BIOS config and parts; `Random` is only in display getters (`GetCpuInternalTemp(core)`, `GetGpuInternalTemp`, `GetCaseInternalTemp`), Power Monitor and airflow node noise. No pause or `timeScale` dependency.
- Command 14 `Simulation`: `Failure` (host only; a guest holds back its own non-forced `ComputerSim.EmergencyShutdown` on shared PCs and runs the host's with `Force` inside `NativeProjection`) and `Fans` (curves keyed by native part path, else the nearest listed part above the fan: a radiator's fans are separate part objects at run time).
- Native startup can call `VirtualComputer.BlueScreenOfDeath` directly with `CPU_HEAT`. The 0.45 hook shares that failure through the same command. `ComputerSim.EmergencyShutdown` sets `BSODActive` before calling the display, so the startup hook skips the ordinary simulation path. 0.46 shares each reason once per boot and clears that record on native `ComputerSim.TurnOn`, which also runs on Restart.
- GPU Tuner `OnApply` is one native function with its button lambda: hook `OnApply` only. Its Apply/Reset become a `BiosChange` with `Live` (written in place + `AirflowSim.RefreshSimData`, no restart); both games put their own write back after the native call.
- The game seems not to save Fan Control curves in Free Build (`SaveFanControllerData` has only a career caller); the host re-sends them when a guest arrives. App IDs: `GPUTUNER`, `FANCONTROL`, `OCCT`, `ADDPROGRAM`. Probe commands: `sim-report`, `sim-fail`, `launch`, `tuner`, `fans` (phase 6 probe).

## Working rules

1. Check `git status` and keep unrelated edits. Commit or push only when the owner asks.
2. Keep Unity/IL2CPP calls on the main thread; `CoopSession.Poll()` raises events there.
3. Ask the owner before design decisions (UI placement, flow, what gets synced). Don't assume.
4. Separate what was verified in the running game from what was only read in the decompile.
5. Leave the owner's own game processes and saves alone. Close only the instances you started.
6. Commit Unity work separately from mod work, with a commit message starting `[unity]`. Unity work is everything under `unity/` plus the built bundle `src/PCBS2Coop.Plugin/Assets/pcbs2coop-player.bundle` (and docs that only describe it, e.g. `docs/playermodel.md`). Plugin, network, test and script changes go in ordinary commits, never mixed into a `[unity]` one.
