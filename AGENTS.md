# Agent instructions

PCBS2 Coop is a BepInEx 6 IL2CPP multiplayer mod for PC Building Simulator 2 (Unity 6000.2.6f2, Windows x64). Current state: two players on a LAN share one Free Build world. The host loads a co-op world (Host → New world / Continue, saved in `Saves\Coop`); a guest can join at any time and loads a snapshot of the host's current world; each sees the other as a capsule. Live edits to parts, PCs and benches after the join are not synced yet (phase 3 onward).

## Layout

| Path | What it is |
| --- | --- |
| `src/PCBS2Coop.Network` | Unity-free layer over LiteNetLib 2.1.4: `CoopSession` (one host, one guest, identity handshake, guest admission), `Compatibility` (refuse a different mod version or game build, warn DLC/catalog), `WorldSync` (host-ordered world changes, snapshot position, hold/replay), `WorldTransfer` (chunked, hashed snapshots), `Identity` + `ObjectRegistry` (player/operation/object IDs), `Protocol` (message types, limits) |
| `src/PCBS2Coop.Plugin` | BepInEx plugin (`PCBS2Coop.dll`): `CoopRunner` main-thread driver, `MultiplayerMenu` + `CoopDialog` main-menu UI, `CoopController` session/world lifecycle/snapshots/remote view, `CoopSaves` co-op save folders, `WorldReadiness` load barrier, `GamePatches` (save hook), `GameInfo` local identity, `WorldHandlers`, `RemotePlayerView` capsule + name tag, `Diagnostics` census, `AutoTest`, `Probe` (audit probe, `PCBS2COOP_PROBE=1` with the self test) |
| `tests/PCBS2Coop.Network.Tests` | Network acceptance tests (`dotnet run`): identity/compatibility, in-memory fault injection for `WorldSync`, admission and snapshot transfer, UDP loopback sessions |
| `scripts/Install-Loader.ps1` / `Uninstall-Loader.ps1` | Install BepInEx be.791 into the game with a rollback manifest in `.local/` |
| `il2cpp-decompile.md`, `tools/decompile/` | How the decompiled workspace in `artiffacts/` was produced |
| `artiffacts/` (ignored) | Decompiled game, ISIL, Ghidra project, BepInEx download |

## Build and test

```powershell
dotnet run --project tests/PCBS2Coop.Network.Tests -c Release   # network loopback test
dotnet build PCBS2Coop.sln -c Release                           # builds and copies the plugin into <GameDir>\BepInEx\plugins\PCBS2Coop
```

No machine-specific path is committed. Set your game folder once: copy `Directory.Build.local.props.example` to `Directory.Build.local.props` (git-ignored) and fill in `GameDir`, or set `PCBS2_GAME_DIR`, or pass `-p:GameDir=...`. The PowerShell scripts read the same file/variables (`scripts/LocalPaths.ps1`; `GhidraHome`/`GHIDRA_HOME` and `Cpp2ILPath`/`CPP2IL_PATH` for the decompile tools). Never write a real local path into tracked files, docs or commit messages; use `<GameDir>`. The deploy copy can't replace the DLLs while the game is running (they are locked), even when the build prints "Deployed"; close the game, rebuild, and compare the deployed `PCBS2Coop.dll` with `bin/Release` before a test run. Build against the real `BepInEx/interop` generated by a first launch, never against the decompiled dummy DLLs.

### Two-instance self test

Set `PCBS2COOP_AUTOTEST=host` for one launch of `PCBS2.exe` and `=join` for a second (working directory `<GameDir>`). Each instance first redirects the game's save folder to a fresh `BepInEx\PCBS2Coop-diag\saves-<role>` (the owner's `Saves` folder is never used; an overwrite prompt is only auto-accepted inside that folder) and clicks with real pointer events. Round 1: host → New world, three markers; guest joins ~30 s later and loads the host's world (the host adds one marker while it loads); both aim at the other's capsule and screenshot; five markers each (guest also one invalid); host pauses, then saves (guest must get the copy); `AUTOTEST: world summary …` and `PASSED/FAILED` on both (summaries must match); host leaves, guest must return to the menu with the reason. Round 2: host → Continue, guest rejoins, guest leaves first, host keeps hosting. Each side ends with `AUTOTEST: finished.` (about two minutes). Census files and screenshots go to `<GameDir>\BepInEx\PCBS2Coop-diag\`. Logs: `BepInEx\LogOutput.log` (first instance) and `LogOutput.1.log` (second). Normal launches never run this. `PCBS2COOP_DIAG=1` writes census files without the self test.

## Versioning

The mod has one version: `<Version>` in `Directory.Build.props` (currently 0.3). It is the plugin version, the network assembly version and the join check; there is no separate protocol version. Two players can join only with exactly the same version, so bump it whenever a build changes what goes over the network or into co-op saves, and before handing a build to someone.

- Each bump adds one to the number after the dot: 0.1, 0.2, 0.3, 0.4, … (0.9 is followed by 0.10).
- BepInEx shows it with a third part (0.3 → `0.3.0`). Only an exact match matters for joining.

## Findings the code depends on

- Main menu: `MainMenuHUD/NewMainMenu/MainMenu/Button2-FreeBuild` has sub-buttons `ContinueFreebuild`, `LoadGame`, `NewGame`. Their actions are attached to each sub-button's `Button.onClick` at runtime, so `Instantiate` copies don't inherit them. The `CustomEventTrigger` on them has no entries.
- The menu activates panels one at a time while fading in; a cloned panel must follow the source's active state and `CanvasGroup` alpha.
- `NewMainMenu.PlayFree()` starts a new Free Build in scene `Stage_02_Workshop`. If a Free Build save exists it first shows `MessageBox.Show("New Game", ...)`.
- Workshop player: root `Player` (`CharacterController`, `Walk`) with child `Main Camera` (`MouseLook`).
- HDRP: Unity's default primitive material doesn't render. Copy an `HDRP/Lit` material already in the scene.
- Unity 6 interop `CoreModule` exports its own `NullableAttribute`, so the plugin project builds with `<Nullable>disable</Nullable>`. Lambdas taking parameters from nullable-annotated Network events need explicit parameter types.
- `Input.inputString` is stripped. TMP input fields work through the game's `InputModule`.
- Saves: `SaveLoadSystem.s_saveDir` is the relative path `Saves`, i.e. `<GameDir>\Saves`, shared by every local instance. Redirecting `s_saveDir` on the main menu also redirects PlayFree's existing-save check (run R1). The game lists only the top level of that folder. Saves are `<name>.binary.zip` with one `<name>.binary` entry.
- `CreateSaveGame(name)` fixes the target path at call time (safe to restore `s_saveDir` right after), writes on a thread (`WaitingOnThread()`), and makes that file the game's current save name (`LevelLoadPersistency.SaveName`, `SetOpenedSaveName`): restore both after a side save. Every save path goes through it; Harmony hooks on it fire for native callers.
- `NewMainMenu.ContinueFreeBuild(name)` loads a named save from the current `s_saveDir` (name = the save list's `m_name`, e.g. `coopworld.binary`). A new Free Build loads the shipped `StreamingAssets/UtilitySaves/defaultFreebuild.binary` when a copy is in the save folder, otherwise the workshop starts empty.
- `NewLoadingScreen.LoadScene("Main_Menu", false)` returns to a working main menu. Pause only sets `GameController.paused`; `Time.timeScale` stays 1 and `Application.runInBackground` is already on.
- Players spawn at the player position stored in the save, so a joining guest starts where the host's save placed the player.
- Identity: `Application.version` is just `0.1`; the build GUID comes from `PCBS2_Data\boot.config`. The part catalog (`PartsDatabase.s_instance.m_parts`, 2816 parts) is already loaded on the main menu. Parts, PCs and benches have no instance IDs in game data; the mod assigns `NetObjectId`s.
- The game has its own global type named `Compatibility`; use `PCBS2Coop.Network.Compatibility` in the plugin.
- LiteNetLib 2.1.4 throws `InvalidOperationException` on short reads; parsers use `Protocol.IsReadError`. Don't use `PutBytesWithLength`; use `Protocol.WriteBlob`/`ReadBlob`.

## Synchronization contracts (phase 1)

- The host orders every world change. Guests submit requests through `Session.World.Submit`; a change takes effect on both peers only when the host's confirmed `Mutation` arrives. Register one `ICommandHandler` per command type in `CoopController.OnWorldCreated`.
- `Validate` runs on the host only. `Apply` runs on both peers in revision order on the main thread; it must make the change only, never trigger game paths that submit another change.
- A world generation is one incarnation of the world (host starts it with `BeginGeneration`, never from inside `Apply`). Requests/changes from another generation are refused or dropped.
- Remote players' activity is per-actor data. Never write it into `GameController`/`WorkshopController` singleton fields.
- Details and evidence: `docs/audit/phase-1.md`.

## World lifecycle contracts (phase 2)

- A joined guest is not in the world until it loads a host snapshot (`CoopSession.GuestNeedsWorld` → `BeginSnapshot` in the same frame as the game save → `SetSnapshotFile`; guest `SnapshotReceived` → load → `CompleteAdmission`). World changes after the snapshot mark are held and applied after the load. Mod-side state a late joiner needs goes in an `IWorldState` registered on the world.
- The host starts a world generation only when its world is ready (`WorldReadiness`). A guest that receives a new generation after admission leaves to the menu.
- While a co-op world is loaded, `s_saveDir` points into `<saves>/Coop` (host: `Coop`; guest: `Coop/GuestSession`, copies in `Coop/Joined`); it is restored only on the main menu (`CoopSaves`).
- No shared pause: nothing in the session may depend on the game's pause flag.
- Details and evidence: `docs/audit/phase-2.md`.

## Working rules

1. Check `git status` and keep unrelated edits. Commit or push only when the owner asks.
2. Keep Unity/IL2CPP calls on the main thread; `CoopSession.Poll()` raises events there.
3. Ask the owner before design decisions (UI placement, flow, what gets synced). Don't assume.
4. Separate what was verified in the running game from what was only read in the decompile.
5. Leave the owner's own game processes and saves alone. Close only the instances you started.
